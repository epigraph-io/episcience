# Runbook: provision a group's wiki curator agent

A wiki article is generated by `wiki_generate_article` running as a **curator
agent**. Each group has its own curator, and the curator belongs to that group
and no other: `group:main` first. This runbook provisions the `group:main`
curator. Phase D's nightly `wiki-curator` schedule (EpiClaw) authenticates as
this agent.

**No code path creates this identity.** Neither episcience nor the kernel nor
EpiClaw provisions a curator, and nothing repairs one that is wrong. It is an
operator action, done once per group, by hand, with the steps below.

Everything specific to the live deployment (the group's UUID, the curator's
agent id, URLs, where its key is stored) goes in ops-private, never in this
public repo. Below it appears as `<placeholders>`.

## Why "one group" is the whole guarantee

An article must be written with **exactly its group's read scope**: public
claims plus that group's own claims (plan
`docs/superpowers/plans/2026-10-07-epigraph-wiki.md`, "Risks: visibility
leakage"). The pipeline reads as the agent that calls the tool, so the
curator's memberships ARE the article's read scope.

- Today, Stage 1's seed filter keeps only public claims and the owner group's
  claims, and the worker runs with `EmptyEdgeProvider`, so nothing is added
  after seeding.
- **Once a real edge provider lands, Stage 2's 2-hop traversal reads with the
  acting principal's full scope.** A curator that is also a member of a second
  group then pulls that group's private claims into the subgraph a `group:main`
  article is written from. **A curator in two groups breaks the visibility
  guarantee.** Do not rely on later layers to catch it.

The one exception is the curator's **own personal group**
(`did:epigraph:personal:<curator-agent-id>`). The kernel provisions it for an
agent on its own, e.g. when it resolves the agent's default ownership. It is
harmless only while it is empty, which holds as long as:

- the curator **authors no kernel claims**; and
- the curator **is never linked to an operator**, in either direction. An
  operator link (`operator_links`, the `OPERATED_BY` lineage) gives the agent a
  `writer` membership in the operator's personal group, which is a second,
  private group.

The check in step 5 enforces all of this.

## What you need

- An access token holding `agents:write`, for registering the agent.
- An access token for a live **admin** of `group:main` that holds the
  `groups:admin` scope. Adding a member needs both the scope and the
  membership.
- `group:main`'s group base key and that admin's Ed25519 secret key, each as
  a hex **file** in the scratch directory: `group-main.base.hex` and
  `admin.secret.hex`. Never type or paste either value into a command line.
  If you don't hold the base key directly, step 3 recovers it from the
  admin's own share straight into its file.
- `epigraph-group`, built from the kernel rev pinned in `docs/kernel-pin.md`
  (`crates/epigraph-cli`, binary `epigraph-group`), installed on **your own
  workstation**. Never run it on the production host or any other shared
  machine (see below).
- A Postgres login on the kernel database whose `session_user` is a member of
  `epigraph_maintenance`, for the read-only check.
- `group:main`'s UUID (`<group-main-id>`) and the kernel API URL
  (`$EPIGRAPH_URL`), both from ops-private.

### Where the key ceremony runs, and how secrets stay off the record

Steps 1 and 3 handle key material: the curator's new secret key,
`group:main`'s base key (which decrypts every `group:main` ciphertext and lets
whoever holds it wrap shares for new members) and an admin's secret key. Do
them on **your own workstation**, never on the production host or any other
machine where someone else can log in. `epigraph-group` was built for this: it
works on the caller's own machine and opens no network or database connection.

`epigraph-group` takes keys only as `--flag <hex>` arguments. It has no stdin
or file input. So:

- **Keep secrets in files, never on the command line.** Pass them as
  `"$(cat <file>)"`. History then records the `$(cat ...)` text, not the key.
- **Start each command that reads a secret file with a space**, with
  `HISTCONTROL=ignorespace` (or `ignoreboth`) set, so the shell does not
  record the line at all. The commands below include the space.
- **Substitution does not hide the value from the process table.** The shell
  expands `$(cat ...)` before `epigraph-group` starts, so the key is in its
  argv, readable through `ps` and `/proc/<pid>/cmdline` while it runs. Only
  running on a single-user workstation closes that hole, which is why the
  workstation rule above is not optional.

Work in a fresh `0700` scratch directory on that workstation:

```sh
export HISTCONTROL=ignorespace
umask 077
mkdir -m 700 curator-scratch && cd curator-scratch
```

`epigraph-group` prints secrets to stdout, so redirect them to files and keep
key material out of tickets and chat. Delete the directory once step 4 is
done.

## 1. Mint a fresh Ed25519 key, offline

On your workstation, in the scratch directory:

```sh
umask 077
openssl genpkey -algorithm ed25519 -out curator.pem
openssl pkey -in curator.pem -pubout -outform DER | tail -c 32 | xxd -p -c 64 > curator.pub.hex
openssl pkey -in curator.pem -outform DER         | tail -c 32 | xxd -p -c 64 > curator.secret.hex
```

**Always use a new key.** Registering a key that already names an agent
returns that existing agent and provisions **no** OAuth client for it.

## 2. Register the agent through the kernel's normal registration path

```sh
curl -sS -X POST "$EPIGRAPH_URL/api/v1/agents" \
  -H "Authorization: Bearer $AGENTS_WRITE_TOKEN" -H 'Content-Type: application/json' \
  -d "{\"public_key\": \"$(cat curator.pub.hex)\",
       \"display_name\": \"wiki-curator group:main\",
       \"labels\": [\"software_agent\"]}"
```

Record the returned `id` as `<curator-agent-id>` in ops-private.

Because the call is authenticated, the kernel also creates the agent's OAuth
client:

- its `client_id` is the public-key hex;
- its scopes are the agent default set (`claims:read`, `claims:write` and the
  other agent scopes, never an admin scope);
- its status is `active`;
- it has no client secret, because agents authenticate by Ed25519 assertion.

A failure here is only logged by the kernel, so step 5 checks that the client
exists.

Do **not** create the curator any other way:

- not through `/oauth/register`, which registers a pending, keyless principal;
- not by reusing an existing agent;
- not through any path that links it to an operator (the `OPERATED_BY` / LLM
  agent identity flows).

## 3. Grant membership in `group:main` only, as `writer`

`wiki_generate_article` refuses an owner group the caller cannot write, so the
role must be `writer`. `epigraph-group wrap` defaults to `reader`, which the
tool refuses. The curator does not need `admin`. Read the group's active epoch
from the API rather than assuming it:

```sh
curl -sS "$EPIGRAPH_URL/api/v1/groups/<group-main-id>" \
  -H "Authorization: Bearer $GROUP_ADMIN_TOKEN"            # note current_epoch
```

If you don't hold `group-main.base.hex` directly, recover the base key from
the admin's own share at `current_epoch` into it. The admin's secret comes from
`admin.secret.hex`, and the base key never reaches the terminal:

```sh
 epigraph-group unwrap \
   --member-secret "$(cat admin.secret.hex)" \
   --wrapped-key-share <admin-share-hex> \
   --admin-public <share-wrapping-admin-public-hex> \
   --group-id <group-main-id> \
   --epoch <current_epoch> \
   --member-agent-id <admin-agent-id> \
   | jq -r .base_key > group-main.base.hex
```

Then wrap the base key for the curator. Both secrets are read from their
files, and the line starts with a space so it stays out of history:

```sh
 epigraph-group wrap \
   --base-key "$(cat group-main.base.hex)" \
   --admin-secret "$(cat admin.secret.hex)" \
   --member-public "$(cat curator.pub.hex)" \
   --group-id <group-main-id> \
   --epoch <current_epoch> \
   --member-agent-id <curator-agent-id> \
   --role writer > member-body.json

curl -sS -X POST "$EPIGRAPH_URL/api/v1/groups/<group-main-id>/members" \
  -H "Authorization: Bearer $GROUP_ADMIN_TOKEN" -H 'Content-Type: application/json' \
  -d @member-body.json
```

Add the curator to **no other group**. If a second group needs a wiki, give it
its own curator by running this runbook again with that group.

## 4. Store the credentials in the EpiClaw secret store

The curator's only secret is its **Ed25519 secret key** (`curator.secret.hex`).
Store it, with `<curator-agent-id>` and the `client_id` (the public-key hex), in
the EpiClaw secret store under the curator's own entry. Phase D's schedule
reads it from there. Record where the entry lives in ops-private.

The schedule mints its access tokens itself:

- `POST $EPIGRAPH_URL/oauth/token` with `grant_type=client_credentials`;
- `client_id=<public-key hex>`;
- `client_assertion_type=urn:epigraph:ed25519`;
- `client_assertion = base64(timestamp(8 bytes, big-endian) || nonce(16 bytes) || Ed25519 signature over those 24 bytes)`.

Nothing long-lived besides the key needs storing.

Then delete the scratch directory and everything in it: `curator.pem`,
`curator.pub.hex`, `curator.secret.hex`, `group-main.base.hex`,
`admin.secret.hex` and `member-body.json`. The base key and the admin's
secret must not outlive the ceremony on the workstation either.

## 5. Verify, read-only: one group, plus at most its own empty personal group

Run these on the kernel database **as the maintenance login**. Under forced
row security, an ordinary application session sees no membership or operator
link rows, and the checks would then pass vacuously. The first statement guards
against that. The maintenance role can read every table used here:

- `group_memberships`, `groups` and `claims` (tenancy contract C10);
- `operator_links` (an explicit grant, and its read policy admits only a
  maintenance session);
- `oauth_clients` (no row policy).

Each check is its own statement, so a failure in one cannot hide the others.

```sql
\set curator '<curator-agent-id>'
\set main    '<group-main-id>'

-- 1. The session can see every row: must be t.
SELECT public.epigraph_bypass() AS maintenance_session;

-- 2. The curator's live groups: must list group:main (role writer) and at most
--    its own personal group (kind 'personal', did_key
--    'did:epigraph:personal:<curator-agent-id>'), nothing else.
SELECT DISTINCT g.id, g.kind, g.did_key, g.display_name, m.role
  FROM public.group_memberships m
  JOIN public.groups g ON g.id = m.group_id
 WHERE m.agent_id = :'curator'::uuid
   AND m.revoked_at IS NULL
 ORDER BY g.kind, g.id;

-- 3. The same as one verdict: main_writer must be t, other_groups must be 0.
SELECT bool_or(m.group_id = :'main'::uuid AND m.role = 'writer') AS main_writer,
       count(DISTINCT m.group_id) FILTER (
         WHERE m.group_id <> :'main'::uuid
           AND NOT (g.kind = 'personal'
                    AND g.did_key = 'did:epigraph:personal:' || :'curator')
       ) AS other_groups
  FROM public.group_memberships m
  JOIN public.groups g ON g.id = m.group_id
 WHERE m.agent_id = :'curator'::uuid
   AND m.revoked_at IS NULL;

-- 4. No operator link in either direction, retired ones included: must be 0.
SELECT count(*) AS operator_links
  FROM public.operator_links l
 WHERE l.agent_id = :'curator'::uuid OR l.operator_id = :'curator'::uuid;

-- 5. The personal group is empty: must be 0.
SELECT count(*) AS personal_group_claims
  FROM public.claims c
  JOIN public.groups pg ON pg.id = c.owner_group_id
 WHERE pg.did_key = 'did:epigraph:personal:' || :'curator';

-- 6. The OAuth client exists: exactly one row, status 'active', with
--    claims:read and claims:write granted and no admin scope.
SELECT client_id, client_type, status, granted_scopes
  FROM public.oauth_clients
 WHERE agent_id = :'curator'::uuid;
```

Memberships are per key epoch, so the checks count distinct groups, not rows.
Any other answer means the curator must not run. Fix the membership, or
retire the agent and provision a new one. Do not work around it.

Re-run the check whenever group memberships change, and before Phase D's
schedule is first enabled.

## Running as the curator

- **Always pass `owner_group_id = <group-main-id>`** to
  `wiki_generate_article`. Without it, the tool uses the caller's default
  group, which for an agent with no operator link is its personal group: the
  article would be owned by the wrong group.
- The curator calls only the wiki tools and episcience's read tools. It never
  submits kernel claims, since that would fill its personal group.

## Retiring a curator

As a `group:main` admin:

1. Remove the membership with
   `DELETE $EPIGRAPH_URL/api/v1/groups/<group-main-id>/members/<curator-agent-id>`.
   The removal marks the group `reseal_required_at`; rotate the group key as the
   group-key procedure requires.
2. Delete the curator's entry from the EpiClaw secret store.

The articles it wrote stay: they are owned by `group:main`, not by the curator.
